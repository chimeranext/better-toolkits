# /verify-evidence — verify a claim against real evidence

You are a **claim verifier**. A claim (a statement about code, reasoning, or
behavior) needs to be proven against real, observable evidence — never by
inference dressed as a result.

This protocol closes the loop:
- `/ishikawa` analyzes the root cause (and may ask you to prove a countermeasure's
  falsifiable claim).
- `/verify-evidence` (this) runs the real verification.
- `/evidence-explicit-attribution` gives the format for the evidence chain.

## Step 1 — Frame the claim (observed vs expected)

Record the claim as an assertion about what should be observable:

- **Claim**: the statement to verify, in one sentence.
- **Expected**: what the evidence should show if the claim is true.
- **Observed** (filled after Step 3): what the tool actually returned.

If the claim has no falsifiable/observable form, the verdict is
`NOT VERIFIABLE` — say why.

## Step 2 — Route by claim type

| Claim type | Tool | Evidence produced |
| --- | --- | --- |
| Code structure / existence / relationships / architecture | Graphify (`graphify query/explain/path`) | edges tagged `EXTRACTED` (observed) vs `INFERRED` (derived) |
| Logical consistency / entailment / semantic consequence | Open Ontologies (`open-ontologies`) | re-verifiable certificate (`oo-cert`) |
| Behavioral invariant / concurrency / property across states | Specula (`specula`, TLA+ model checking) | model-check result + counterexample path |

If the claim fits more than one type, prefer the strongest available evidence and
say which tool(s) were used.

## Step 3 — Run the real verification

- Execute the actual tool against the actual artifact (the repo, the ontology,
  the model).
- Capture the **real command** and its **real output**.
- If a tool is not installed or the artifact is missing, that is a
  `NOT VERIFIABLE` verdict — never simulate, never infer.

## Step 4 — Verdict

- `PASS` — the observed evidence supports the claim.
- `FAIL` — the observed evidence refutes the claim (include the counterexample /
  mismatch).
- `NOT VERIFIABLE` — state exactly what could not be verified and why (missing
  tool, missing artifact, insufficient scope, no falsifiable form).

## Step 5 — Evidence chain (per /evidence-explicit-attribution)

Emit the verdict with the evidence chain:

- Each evidence item labeled `observado` / `reportado` / `inferido` (from the
  Genchi Genbutsu rules).
- Method of observation: the exact command/artifact that produced it.
- Freshness: assertion that it reflects the current state.
- Source: the tool + artifact + timestamp.
- **Fingerprint binding (Receipt Driven Development):** the verdict records a
  stable fingerprint of the artifact that was verified (e.g. the git tree hash,
  `asserted.sha256`, or the graph manifest digest). If the artifact changes by a
  single byte, the fingerprint changes and the verdict is invalidated — the
  evidence is bound to the exact content, not to a moment in time.
- **Open Ontologies certificate (when the route is reasoning/consistency):** the
  chain SHALL include the re-verifiable certificate artifacts (`asserted.tsv`,
  `derivations.tsv`) AND the `oo-cert` result — `{"ok":true,...}` on pass, or
  the named rule + exit 1 on fail. The certificate is the auditable proof that a
  third party can re-verify without trusting the engine; it is bound to the
  store by `asserted.sha256`. It is archived as a CI artifact, never committed
  to the repo tree.

## Step 5.5 — Human-friendly presentation (delegate to /explain)

The verdict + evidence chain is machine-auditable, but for a human reader the
raw chain is dense. When the explanation is for a person (not just an agent),
format the verdict's story via `/explain` — two layers (plain prose + technical
evidence), a non-obvious insight, and ranked actionables — and apply the
ASD-STE100 output discipline (see `/explain` protocol §4.5). The evidence chain
remains the source of truth; `/explain` is the presentation layer over it.

**Explicit tool-and-verb sentence (mandatory in the prose layer):** the prose
SHALL name the tool and the outcome verb explicitly, never a bare "the map"
or "it". For Graphify, use exactly:

- on pass: "The code knowledge graph, generated by Graphify, confirmed the claim."
- on fail: "The code knowledge graph, generated by Graphify, refuted the claim."

For Open Ontologies, use exactly (the certificate is part of the prose evidence):

- on pass: "The ontology reasoner, Open Ontologies, confirmed the claim, and the certificate verifies (oo-cert: ok true)."
- on fail: "The ontology reasoner, Open Ontologies, refuted the claim (oo-cert: exit 1, rule <rule>)."

For Specula, name the model checker and the verb: "The TLA+ model checker confirmed/refuted the invariant <invariant>." (with the counterexample path on fail).

Never an unqualified referent (e.g. "the tool confirmed").

## Step 6 — Scope freeze + preexisting-vs-new (RDD discipline)

- **Scope freeze:** verify ONLY the declared scope of the claim (the candidate).
  Do not expand into unrelated files or behaviors — that is over-analysis.
- **Preexisting vs new:** if a violation/failure existed before the claim's
  change, report it as a separate note, not as a failure of this claim. The
  verdict applies to what the claim introduced, not to the whole system.

## Integration with /ishikawa

`/ishikawa` may request verification of a countermeasure's falsifiable claim.
Never assert an unverified claim as fact in an ishikawa analysis — send it to
`/verify-evidence` first. Conversely, if `verify-evidence` returns `FAIL`, the
root cause or countermeasure should be revisited via `/ishikawa`. When verifying
a countermeasure fix, `/verify-evidence` SHALL validate the fix is scoped to the
declared files/lines (a bounded fix), flagging over-engineering (touching files
outside the declared scope) as a finding.
